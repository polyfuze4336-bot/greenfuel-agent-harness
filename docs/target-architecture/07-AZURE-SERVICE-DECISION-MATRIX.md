# 07 Azure service decision matrix

Status: proposed, Phase 0. **Nothing here is a decision and no Azure fact in this phase is verified.** The programme brief says services are candidates, selected by requirement, regional availability, cost, operational complexity and trade-offs, not because they exist. Each row therefore states the role the design needs, why a service is considered for it, what else could fill it, what must be verified in each jurisdiction before it can be relied on, and what evidence exists today. "Provisional lean" is where the evaluation points now; it does not authorise creating anything. The existing [candidate evaluation](../azure/AZURE-REFERENCE-ARCHITECTURE.md) and [REGIONAL-AVAILABILITY](../azure/REGIONAL-AVAILABILITY.md) remain the record of what was checked (nothing) and what must be.

## Evidence in hand

The only Azure facts gathered are **public list prices** from the Azure Retail Prices API, retrieved on the date in [azure-prices.json](../business/model/azure-prices.json) by an anonymous request (no subscription, no sign-in, nothing created). A price meter in a region shows an item is **sold** there. It does not show that the service meets any residency rule, that it supports zones or private networking, or that every feature is present. Treat it as weak evidence of existence and nothing more.

How to read the model columns: these count meters for Azure OpenAI and Foundry models whose **names** carry an abbreviation for global or data-zone deployment. It is a heuristic over meter names, **not a statement of where any prompt is processed**, and the abbreviations were not checked against documentation. What it does show is that most model meters in several regions are global-scope by name, so a model being priced in a region is not evidence that its processing stays there. That is exactly why D-028 is open and why the design makes agents optional per cell.

## Selection method

For each role: (1) what requirement drives it, (2) at least one alternative, (3) the residency and control checks per jurisdiction, (4) operating burden, (5) cost drivers (see the [model](../business/BUSINESS-VALUE-MODEL.md)), (6) lock-in and exit. A service is promoted from lean to decision only when the checks are evidenced for **each jurisdiction that would use it** by an approved read-only identity against the approved subscription (T32, T33, not granted), and an ADR records it.

## What this matrix does not do

- It does not verify a single service in a single region. The steps (T32 subscription, T33 read-only identity, then per-service checks) are in [AZURE-READINESS-ASSESSMENT](../azure/AZURE-READINESS-ASSESSMENT.md) and are not granted.
- It does not say any service complies with any standard or law. Hardware assurance levels, certifications and data-handling claims are all unchecked and are not repeated here.
- It does not price anything beyond the list prices in the model, and those are list prices for one sampled region.
- It does not choose between Container Apps and Kubernetes for local cells; it says why that choice depends on D-010.

## Findings that change the design

1. **Agents must be optional per cell** because model processing location is unverified and many model meters appear global-scope (D-028).
2. **Redundancy options are residency decisions**: geo-redundant storage and paired-region vault replication can place copies in another jurisdiction. The design requires zone-redundant or same-jurisdiction replication only.
3. **Management and identity planes are potential paths out.** Arc-style management, global identity, API gateway analytics and monitoring metadata each need a per-service check (SEC-002, D-033).
4. **The largest cloud line in a cell is key custody, not compute** (model section 4), which is the clearest sign that the real costs of this design are sovereignty and operations, not infrastructure scale.
